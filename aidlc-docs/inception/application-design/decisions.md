# Architecture Decisions — ScanLab (LidarApp)

Inputs: `requirements.md`, `stories.md`, `platform-verification.md`, `team-practices.md`
and `application-design-questions.md` (Q1–Q6). No existing `architecture` artefact
applies; the project is greenfield.

Each record gives Context, Decision, Consequences, Alternatives Rejected, Security and
Reversibility. "Core" means the sensor-independent package; "App" means the iPhone app
target. When code lands, the scribe copies the active records into `docs/DECISIONS.md`.

## ADR-001: Build a native Swift and SwiftUI app with no server

**Context:** One user, one phone (NFR-1), fully offline (NFR-2), no data leaving the
phone (NFR-3). Capture needs the platform's depth, tracking and Object Capture
frameworks (FR-3, FR-4), which are native-only. The rough mockups chose the standard
iPhone look.
**Decision:** A single native app written in Swift, with SwiftUI for screens, Swift
concurrency for background work and the Observation framework for screen state. No
backend, no accounts, no network code.
**Consequences:** Direct access to every sensing capability. The owner cannot read Swift
yet, so code must be explained (project rule). All building needs Apple tools on a
hosted Mac (TC1). Nothing is reusable on other platforms.
**Alternatives rejected:** *Cross-platform toolkit (React Native or Flutter)* — the
owner's other app uses one, but depth, scene reconstruction and Object Capture would
each need a hand-written native bridge, doubling the surface with no second platform to
benefit. *Web app* — no access to the depth sensor.
**Security:** No network surface at all; the attack surface is the files the app writes
and the files it opens. Camera permission is the only protected capability.
**Reversibility:** Locked in.

## ADR-002: Stable build tools and minimum iOS 26, moving to iOS 27 tools later

**Context:** The phone runs iOS 27. The hosted build service's stable image has Xcode 26
with iOS 26 SDKs; the Xcode 27 image is a public preview (V9). The owner chose "stable
now, 27 later" (Q1-C).
**Decision:** Build with Xcode 26 on the `macos-26` runner image, deployment target
iOS 26.0, Swift 6 language mode. Revisit when the Xcode 27 image is generally available.
**Consequences:** No iOS 27-only features until the move. The app relies on forward
compatibility to run on iOS 27 (assumption RA2), confirmed by the first delivery.
**Alternatives rejected:** *Preview iOS 27 tools now* — a preview image can change or
break, and every break costs a round trip with no Mac to investigate. *Pin an older
toolset* — Apple requires Xcode 26 or later for uploads.
**Security:** Stable tools receive security fixes; no implication beyond that.
**Reversibility:** Easy — one setting in the build configuration.

## ADR-003: Ports and adapters, with a pure-Swift Core package

**Context:** Sensor code cannot run in the hosted build (PC3), yet the team practice
requires 80% coverage on sensor-independent logic and tests in every build (NFR-10).
The accuracy calculation must be provably right on synthetic input (FR-9.9).
**Decision:** Split the code in two. **ScanLabCore**, a Swift package with no dependency
on camera, depth or interface frameworks, holds geometry, mesh simplification, file
writers, alignment, feature fitting, accuracy reporting, the scan library model and the
log model. It defines **ports** (protocols) for everything it needs from the phone. The
**App** target holds SwiftUI screens and **adapters** that implement the ports with
ARKit, RealityKit, AVFoundation, Vision and the file system. Dependencies point inward:
App depends on Core; Core depends on nothing.
**Consequences:** Core is tested with `swift test` on the build machine with coverage
measured. Adapters stay thin so that what cannot be tested automatically is small and
covered by the on-device checklist. Costs some indirection and more files.
**Alternatives rejected:** *Single app target with tests in the simulator* — depth and
Object Capture do not run there, so most tests could not exist. *Core as a separate
repository* — overhead with one consumer.
**Security:** File parsing and writing are concentrated in Core, where they are tested
against malformed input.
**Reversibility:** Moderate — the boundary is cheap to keep and costly to add later.

## ADR-004: Generate the project file with XcodeGen

**Context:** There is no Mac to open or edit a project file (TC1). The fishing app's
build workflow already generates a project from a manifest when none is committed.
**Decision:** Describe the app in a `project.yml` manifest; XcodeGen generates the
project on the build machine. No `.xcodeproj` is committed.
**Consequences:** The whole project definition is a short text file that can be reviewed
and edited on Windows. XcodeGen (free, MIT) becomes a build-time tool, installed on the
runner. Project settings unknown to XcodeGen need its escape hatches.
**Alternatives rejected:** *Hand-written committed project file* — a large opaque file
that cannot be safely edited without Apple's tools. *Swift package only, no app
project* — a package cannot produce a signed, deliverable app with permissions and
icons.
**Security:** Build-time tool only; not shipped in the app. Version pinned in the
workflow.
**Reversibility:** Easy — a generated project can be committed at any time.

## ADR-005: Sweep capture uses ARKit scene reconstruction

**Context:** FR-3 needs a surface model from moving the phone over a medium or large
subject, with tracking-loss events for guidance (FR-5) and a live depth layer (FR-2).
**Decision:** Use an ARKit world-tracking session with scene reconstruction for the
model, scene depth and its confidence map for the live layers, and ARKit's tracking
state for guidance events. The reconstructed mesh is copied into Core's mesh type at
Finish.
**Consequences:** Least code for a working sweep; tracking, relocalisation and meshing
are the platform's. Mesh detail is whatever ARKit provides (room-oriented, V3), which
the accuracy report will quantify. No control over the meshing itself.
**Alternatives rejected:** *Fuse depth frames ourselves* into a volume and extract a
mesh — full control and possibly finer detail, but a large amount of sensor-dependent
code that cannot be tested in the build; reconsider only if the accuracy figures justify
it. *Camera-framework depth stream without ARKit* — higher still resolution (V1) but no
tracking, so no way to combine views.
**Security:** Camera frames stay in memory; only the mesh is stored.
**Reversibility:** Moderate — behind the `SweepCapturing` port.

## ADR-006: Photo capture uses on-device Object Capture, keeping photographs and poses

**Context:** FR-4 needs a model from photographs with depth for size. The platform
provides guided capture and on-device reconstruction, limited to reduced detail (PC1).
The owner added raw-capture export (FR-7.5).
**Decision:** Use the platform's Object Capture session for guided capture and its
photogrammetry session for reconstruction at the highest detail the phone reports.
Output is requested as OBJ and converted to Core's mesh type. The captured photographs,
depth data and camera poses are kept in the scan's folder when the owner chooses to keep
the raw capture.
**Consequences:** A working photo pipeline with little code, including the platform's
own capture feedback. Detail is capped (PC1), which is the main accuracy risk (R1).
Whether the build continues in the background is unknown (Open Question 3); the adapter
must support resuming from the saved photographs. The platform's capture view limits how
far the capture screen can be customised.
**Alternatives rejected:** *Own photogrammetry on the phone* — far beyond the scope of an
MVP. *Capture on the phone, reconstruct on a server* — breaks NFR-2, NFR-3 and the
no-cost rule. *Capture only, reconstruct on the Windows computer* — makes a third-party
tool mandatory (S4); kept as an optional path through FR-7.5.
**Security:** Photographs may show surroundings; they stay on the phone unless exported
by the owner.
**Reversibility:** Moderate — behind the `PhotoCapturing` port; kept photographs allow
another reconstruction route later.

## ADR-007: One folder per scan with a JSON manifest; no database

**Context:** Scans must survive relaunch, crashes and updates (FR-6.3, NFR-8); storage
per scan must be visible and freeable (NFR-9); raw captures are large.
**Decision:** Each scan is a folder in the app's Application Support area containing a
small JSON manifest (name, method, dates, detail level, flags), the mesh file, a
thumbnail, and optionally the raw capture and accuracy reports. The library is built by
reading manifests. Writes go to a temporary name and are renamed into place.
**Consequences:** Nothing to migrate, easy to inspect and export, storage is a folder
size. Listing cost grows with scan count, acceptable for one user. No queries beyond
sorting.
**Alternatives rejected:** *The platform's object database* — schema migrations are a
known source of data loss on update, with nothing here that needs queries. *A single
library file* — one corrupt write loses every scan.
**Security:** Files are protected by the phone's data protection; the app's storage is
excluded from nothing and shared with no other app.
**Reversibility:** Moderate — behind the `ScanStoring` port; a migration would be needed.

## ADR-008: Platform frameworks by default; exceptions case by case

**Context:** No-cost and no-sign-up rules (NFR-5); the owner chose "case by case"
(Q2-C). The build machine is small (PC5).
**Decision:** Use only Apple's frameworks and our own code unless an exception is
recorded here with its licence and reason. Exceptions so far are **build-time tools
only**: XcodeGen (MIT), SwiftLint (MIT) and CadQuery (Apache 2.0, used only to generate
the reference object). No third-party code ships in the app.
**Consequences:** We own mesh simplification, alignment, fitting and file writing
(ADR-009, ADR-013): more code, all of it in Core and under test. No dependency updates
or supply-chain exposure in the shipped app.
**Alternatives rejected:** *Free libraries wherever convenient* — each adds build time,
licence checks and something the owner cannot evaluate. *No exceptions at all* — would
forbid the linter the team practice requires.
**Security:** Smallest possible supply chain; build tools are version-pinned.
**Reversibility:** Easy — add an exception record.

## ADR-009: Accuracy in two stages — surface deviation, then feature fitting

**Context:** The owner chose automatic comparison (scope Q7-C) with both methods staged
(Q3-C). The report must state match quality and refuse to present figures when the match
is poor (FR-9.3, FR-9.4).
**Decision:** Stage 1: align the scan to the reference shape (a coarse alignment from
overall shape, refined by iterative closest point), then report the distance from the
scanned surface to the reference, per feature region and size class. Match quality is
the residual of the alignment together with the fraction of the reference surface the
scan covers. Stage 2: within each feature region, fit the expected primitive (plane,
cylinder, sphere) to the scan points and compute the feature's dimension, compared with
the owner's caliper value. Initial thresholds (a report is "unreliable" when the
residual exceeds 2 mm or coverage is under 60%) are provisional and tuned on the phone.
**Consequences:** An answer to "how accurate is it?" arrives a stage earlier than the
full report. Both stages run on synthetic scans with known error in the build (FR-9.9).
Alignment error is itself reported, not hidden. Stage 1's figures are surface distances,
not dimensions, and must be labelled as such.
**Alternatives rejected:** *Feature fitting only* — fragile on rough scans, and gives
nothing if fitting fails. *Surface deviation only* — cannot produce the per-feature
caliper comparison the requirement asks for. *Owner picks alignment points by hand* —
simpler, but the owner asked for no manual measuring.
**Security:** None.
**Reversibility:** Easy — pure Core code.

## ADR-010: Generate the reference object from a CadQuery script

**Context:** The app needs the reference object's exact shape and a feature table; the
owner needs a printable file and something Fusion opens (FR-8). The owner chose a script
(Q4-A). Drift between shape, table and print would invalidate every accuracy figure.
**Decision:** A Python script using CadQuery (free, Apache 2.0) defines the object
parametrically and writes four outputs from one run: an STL to print, a STEP file for
Fusion, a feature table (identifier, kind, design value, region) as JSON that is bundled
in the app, and the owner's measurement sheet. Generated files are committed so the
owner need not run the script.
**Consequences:** One source of truth. Changing the object is a text edit and a re-run.
CadQuery must be installed wherever the script is run (the Windows computer or a build
job); it is not part of the app. The owner edits the design through the script or the
STEP file, not a native Fusion design.
**Alternatives rejected:** *Design in Fusion* — familiar to the owner, but the feature
table would be kept by hand and could drift. *OpenSCAD* — free and text-based, but
cannot write STEP, so Fusion would only get a mesh.
**Security:** The script runs only on the owner's computer or the build machine.
**Reversibility:** Easy.

## ADR-011: Append-only diagnostics log behind one logging port

**Context:** With no Mac, faults must be diagnosable from the phone (FR-10, project
rule "always make new behaviour visible in diagnostics").
**Decision:** Core defines a `Logging` port. The adapter appends one JSON line per event
to a file, flushed on every write, trimmed to the most recent 5,000 lines on launch, and
mirrored to the system log. Every component receives the logger; none writes to the
console directly. The Diagnostics screen reads the same file.
**Consequences:** Entries survive crashes. One place to export. A lint rule forbids
direct console printing so the convention is enforced by the build.
**Alternatives rejected:** *System log only* — unreadable without a Mac. *A third-party
crash and analytics service* — breaks NFR-3 and the no-sign-up rule.
**Security:** The log must never contain photographs or file contents; it records event
names, counts, durations and error reasons only.
**Reversibility:** Easy.

## ADR-012: Edge detection with the Vision framework

**Context:** FR-2.1 and FR-6.5 need edges from the camera shown live and on a scan.
**Decision:** Run the platform's contour detection on camera frames at a reduced rate
and draw the result as a layer. On scan detail, edges are shown over the scan's source
picture. Projecting edges into 3D is not attempted in the MVP.
**Consequences:** Low effort and low risk; satisfies the exploration aim. Does not yet
improve the model itself, which is what the owner ultimately hopes cameras can do; that
belongs with multi-camera work (later scope).
**Alternatives rejected:** *Our own edge filter on the graphics processor* — more
control over tuning but more sensor-side code for the same picture. *Edges derived from
depth discontinuities* — limited by the coarse depth grid; worth adding as a second
layer later.
**Security:** None.
**Reversibility:** Easy — behind the `EdgeDetecting` port.

## ADR-013: Mesh simplification and STL/OBJ writers in Core

**Context:** Fusion needs 10,000 faces or fewer (PC2, FR-7.3); exports must be true-size
millimetres (FR-7.2); native export of other types is unconfirmed (V10).
**Decision:** Implement quadric-error mesh simplification and binary STL and OBJ writers
in Core, with millimetres as the export unit. 3MF is deferred (FR-7.6, Could).
**Consequences:** Export behaviour is identical on the build machine and the phone and
is fully tested, including face-count limits and scale. More code than calling the
platform's model exporter; simplification quality is ours to get right.
**Alternatives rejected:** *The platform's model input/output framework* — convenient,
but its behaviour could only be checked on the phone and it offers no simplification.
*An open-source mesh library* — a shipped dependency for two well-understood algorithms.
**Security:** Writers produce files only at a location the owner chooses.
**Reversibility:** Easy.

## ADR-014: Reuse the fishing app's build workflow; deliver on merge; monthly rebuild

**Status:** Superseded by ADR-016 (2026-11-10, Bolt 1).

**Context:** A working build-and-deliver workflow exists in the Nathans Fishing App
repository (feasibility Q3). The team practice is delivery on every merge; builds expire
after 90 days (V8).
**Decision:** Copy that workflow and its configuration file into this repository,
configured for a native XcodeGen project. Before the build it runs formatting and lint
checks and Core's tests with coverage; any failure stops delivery. It runs on every push
to `main`, on demand, and on a monthly schedule. Signing material lives only in the
repository's secret store.
**Consequences:** Signing and upload are not re-solved. The workflow is general-purpose
and larger than this app needs. The secrets must be added to the new repository by the
owner. A failed scheduled build needs the owner's attention within the remaining window.
**Alternatives rejected:** *A new minimal workflow* — smaller, but re-solves signing
with no Mac to debug it. *A hosted third-party build service* — needs a sign-up.
**Security:** The repository is public: secrets are never echoed, pull requests from
forks do not receive secrets, and third-party workflow steps are pinned to a commit.
**Reversibility:** Easy.

## ADR-015: Name the app ScanLab; license the repository MIT

**Context:** Owner's answers Q5-B and Q6-A; RAID issue I3 required a licence before
publishing.
**Decision:** The app's display name is **ScanLab**. The repository keeps the name
LidarApp and carries the MIT licence. The app identifier is set when signing is
configured, under the owner's existing developer account.
**Consequences:** Code may be reused by anyone with attribution. The repository and app
names differ, which the documentation must state once.
**Alternatives rejected:** *Apache 2.0* — adds a patent grant not needed here. *No
licence* — public code with no stated rights invites confusion.
**Security:** None.
**Reversibility:** Easy.

## ADR-016: Deliver with the builder CLI from the PC; CI checks on every push

**Status:** Active (2026-11-10, Bolt 1). Supersedes ADR-014.
**Context:** At the start of Bolt 1 it turned out that the owner's existing
GitHub-to-TestFlight setup is the **builder** command-line tool (v0.11.0) on the Windows
PC, not a self-contained workflow. Its GitHub workflow (`ios-build.yml`, installed by
`builder init`) only builds and signs; uploading to App Store Connect and handing the
build to TestFlight is done from the PC with an App Store Connect API key stored there.
`builder signing setup` creates certificates and profiles and stores them as repository
secrets with no Mac. ADR-014 assumed delivery would happen inside GitHub on every merge.
**Decision:** Owner's choice (Bolt 1 Q1-A). A separate `ci.yml` runs the secrets check,
lint, format, Core tests with coverage and an unsigned app compile on every push and pull
request. After each Bolt merges, the agent runs `builder ios release --profile store`
from the PC, which builds a snapshot on GitHub, uploads, waits for processing and adds
the build to the internal TestFlight group. `ios-build.yml` is builder-managed and not
edited by hand. The monthly rebuild (FR-1.4) becomes a reminder on the PC.
**Consequences:** The App Store Connect key never enters the public repository. Every
merge is still delivered, but by the agent, not by GitHub; delivery depends on the PC and
the builder tool. The team practice "every merge delivers automatically" is met in
effect, not literally, and is recorded as a project-level decision.
**Alternatives rejected:** *Upload from GitHub on merge* (ADR-014) — requires putting the
App Store Connect key in a public repository's secrets, and a hand-written upload step
the owner's tool already provides. *Write our own workflow* — re-solves signing that
builder already handles.
**Security:** Key material stays in `C:\Users\natys\.scanlab-signing` and builder's
credential store; only the signing secrets are in GitHub, never echoed and not given to
forked pull requests. `.gitignore` and a CI step block key files.
**Reversibility:** Easy — an upload step can be added to a workflow later.

## Not Applicable

- **Cloud platform mapping:** there is no cloud component. No cloud services, accounts
  or infrastructure are designed.
- **Service-to-service communication:** there is one process; components call each other
  directly and through Swift concurrency.
